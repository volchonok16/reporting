# Производительность

Целевой сценарий — 700 000 raw-строк без квадратичного накопления результата.
Скрипт `scripts/performance_test.py` создает CSV потоково, импортирует его через
штатный `CsvImporter`, группирует в SQLite spool, потоково пишет результат,
строит поисковый индекс и выполняет индексный поиск по B.

Запуск целевого прогона:

```bash
.venv/bin/python scripts/performance_test.py \
  --rows 700000 \
  --unique-a 100000 \
  --json-output performance-result.json
```

Метрики в stdout и JSON:

- время генерации входа;
- время импорта/группировки;
- время экспорта;
- время однократного построения поискового индекса;
- время повторного точного поиска по B и широкого поиска по номеру без
  чтения исходника;
- максимальный RSS процесса;
- максимальный наблюдавшийся размер workspace;
- размеры входа и результата;
- фактические количества уникальных A/B и строк результата;
- число замен пустого B и удаленных дублей.

Для повторяемого CI-порога доступны:

```bash
.venv/bin/python scripts/performance_test.py \
  --max-seconds 300 \
  --max-rss-mb 1200 \
  --max-search-ms 500
```

Пороги зависят от runner-а, поэтому по умолчанию скрипт проверяет только
корректность счетчиков. Для быстрой локальной проверки используйте
`--rows 10000 --unique-a 2000`.

SQLite использует файловый spool и индекс `(a_number, sequence)`. Объем
workspace включает вход, spool/WAL/SHM, отчет и результат. `ru_maxrss` —
процессный high-water mark; на Linux он переводится из KiB, на macOS уже
возвращается в байтах.

Результаты полного прогона следует фиксировать вместе с ОС, версией Python,
CPU, доступной памятью и параметрами запуска. Не переносите временный workspace
в репозиторий: он содержит чувствительные номера.

## Контрольный прогон

27 июля 2026 года выполнен полный локальный прогон на macOS arm64, Python
3.12.13, с `--rows 700000 --unique-a 100000 --max-seconds 300
--max-rss-mb 1200`:

| Метрика | Результат |
|---|---:|
| Импорт и группировка | 3,784 с |
| Экспорт | 0,764 с |
| Всего обработка | 4,548 с |
| Однократное построение поискового индекса | 3,248 с |
| Повторный точный поиск по B | 0,000334 с |
| Широкий поиск по номеру `7` | 0,004451 с |
| Максимальный RSS | 73 924 608 байт |
| Максимум временного хранилища | 196 590 651 байт |
| Размер входа | 16 799 960 байт |
| Размер результата | 15 500 088 байт |
| Уникальных A / строк результата | 100 000 / 100 000 |
| B после обработки | 700 000 |
| Пустых B заменено на A | 6 |

Порог времени и памяти пройден. Эти цифры являются ориентиром конкретной
машины, а не универсальным SLA; CI/production baseline нужно измерять на
целевом железе.

## Контроль мастер-файла и восстановления страницы

7 августа 2026 года `scripts/master_load_test.py` проверил 726 779 готовых
строк: 716 000 уникальных опорных номеров и 10 779 повторов. Анализ занял
29,22 с, полное слияние — 18,54 с, пиковый RSS процесса на macOS — около
114 МиБ. Отдельный live-тест через Docker разорвал HTTP-клиент после постановки
анализа в очередь, создал новый клиент с той же сессией и получил завершённый
результат с точными счётчиками. Затем пользовательский браузерный сценарий
обновил страницу на 547 000-й сравнённой строке: интерфейс восстановил прогресс
и показал итог `726 779 = 716 000 + 10 779 + 0 + 0`.
