# Архитектура

## Компоненты

```text
Next/Vinext UI
      |
      | JSON + multipart, X-Session-ID
      v
FastAPI
  ├─ UploadService ── проверка типа, лимитов и владения
  ├─ Importers
  │    ├─ XlsxImporter (read-only)
  │    ├─ XlsImporter
  │    ├─ XlsbImporter (streaming rows)
  │    ├─ CsvImporter
  │    └─ FormattedMappingImporter
  ├─ ValidationService
  ├─ MappingIndexService ── локальный индекс A/B для живого поиска
  ├─ MappingBuilder / MappingParser / MappingSerializer
  ├─ AddMappingsService / DeleteAService / DeleteBService
  ├─ JobService ── bounded thread pool + отмена
  └─ Job workspace
       ├─ исходная неизменяемая копия
       ├─ временная SQLite spool
       ├─ result.csv
       └─ report.csv
```

## Поток обработки

1. Загрузка пишется под случайным именем в приватную директорию задания.
2. После проверки сигнатуры и лимитов объект атомарно публикуется в реестре.
3. Inspect сначала ограниченно читает данные для определения структуры, затем
   по запросу интерфейса возвращает все строки выбранного листа для проверки.
   API-клиент может явно задать ограничение `previewRows`.
4. При первом открытии выбора A/B исходник потоково индексируется в SQLite
   рядом с приватной копией загрузки. Поиск A/B выполняется B-tree range-query
   и больше не перечитывает исходный файл.
5. Фоновое задание потоково читает строки и записывает нормализованные записи
   в SQLite с `sequence` и `source_row`.
6. Дедупликация и порядок обеспечиваются ключами `(a_number, b_number)` и
   порядком первого появления; режим повторов использует отдельный sequence.
7. Ручные связки нормализуются, объединяются с существующими A и
   дедуплицируются в том же SQLite spool.
8. Результат пишется новым временным CSV и атомарно переименовывается только
   после успешного завершения.
9. Результаты и поисковый индекс доступны только владельцу и удаляются по TTL.

Оригинал никогда не меняется. Формулы не вычисляются, макросы не запускаются,
внешние ссылки не открываются.

## Авторизация и роли

`auth_users` хранит локальные учётные записи, роль и разрешение на мастер-файл.
Пароли сохраняются как PBKDF2-хеши с индивидуальной солью. `auth_sessions`
хранит только SHA-256-хеши выданных токенов и срок их действия. Все рабочие
методы API проверяют сессию сервером; мастер-файл дополнительно защищён
проверкой роли или разрешения.

## Постоянный мастер-файл

Мастер-файл хранится в том же локальном SQLite volume, но, в отличие от
загрузок и заданий, не участвует в TTL-очистке. `master_records` содержит
стабильный внутренний ID, естественный ключ A, упорядоченный список B,
параметр, внутренний комментарий, версию строки и soft-delete. `master_changes`
хранит неизменяемые
снимки до/после, ревизию, номер строки, источник слияния и время изменения.
`master_edit_lock` хранит эксклюзивного владельца редактирования и хеш его
авторизационной сессии. Блокировка сохраняется после обновления страницы и
перезапуска API, но автоматически удаляется при выходе, истечении сессии,
сбросе пароля, деактивации пользователя или отзыве доступа к мастер-файлу.
Чтение списка и истории доступно всем пользователям с разрешением, но импорт,
слияние, экспорт и CRUD дополнительно проверяют владельца блокировки на сервере.
Полная очистка дополнительно требует роль суперюзера и полностью опустошает
`master_records` (TRUNCATE) в рамках одной ревизии; в `master_changes`
остаётся одна запись `cleared` с числом удалённых строк, без построчных
снимков.
Суперюзер-владелец блокировки может отдельно удалить журнал и данные прошлых
импортов, отбросить soft-delete строки и превратить активные записи в новую
базовую точку с общей ревизией `T2-0`, версией строки `1` и сохранёнными ID.
Несохранённое состояние редактора и решения по слиянию сохраняются клиентом
отдельно для каждого пользователя и предлагаются к восстановлению после
следующей авторизации.

Импорт выполняется в два этапа. Анализ создаёт долговечную запись задания,
потоково разбирает CSV во временный SQLite spool, а затем пакетами записывает
результат сравнения в основную SQLite-базу. В памяти одновременно находится
не более одной небольшой пачки строк. Статус и число обработанных строк
сохраняются на сервере; после обновления страницы интерфейс находит активный
`importId` по сессии и продолжает опрос. Незавершённые анализы возобновляются
и после перезапуска API, пока исходная загрузка доступна по TTL.

Анализ фиксирует номер текущей master-ревизии и классифицирует строки как
новые, совпадающие или конфликтные. Новые строки анализа выдаются интерфейсу
страницами по 200 и могут быть изменены до применения. Слияние
запускается транзакцией
`BEGIN IMMEDIATE`; если master успел измениться после анализа, операция
отклоняется и требует повторного сравнения. Новые записи применяются
автоматически, конфликтные — только по переданному решению. Отсутствующие во
входящем файле master-строки не удаляются.

`master_duplicate_findings` хранит группы одинаковых опорных номеров готового
файла и номера исходных строк для каждого предложения на слияние. Master
по-прежнему сохраняет одну строку и один стабильный ID на опорный номер, но
интерфейс подсвечивает результаты проверки последнего применённого слияния и
последовательно переходит к каждому найденному повтору.

По умолчанию мастер принимает до 20 000 000 строк
(`CAROUSEL_MAX_MASTER_ROWS`). Это явная проверяемая граница: превышение
возвращает ошибку `MASTER_ROW_LIMIT`, молчаливого обрезания нет. Физические
строки с одинаковым опорным номером не теряются: при импорте интерфейс
предлагает сохранить их отдельными master-строками или объединить АОН в одну
логическую строку. Сводка отдельно показывает `sourceRows`, `uniqueA`,
`duplicateA`, `invalidRows` и `skippedRows`.

## Масштабирование

Горячий путь формирования результата выполняет один проход по входу и один
проход по сгруппированным данным. Его основное состояние хранится в SQLite.
Полный ответ inspect по требованию интерфейса растёт вместе с числом строк
выбранного листа; ограниченные API-клиенты могут передать `previewRows`.
Индексы по A и B ускоряют живой поиск и точные удаления. В локальной поставке
JobService использует ограниченный thread pool. Для нескольких реплик его
интерфейс заменяется очередью задач без изменения бизнес-сервисов.

## Развертывание

Docker Compose запускает API и web. В production временное хранилище должно
быть отдельным зашифрованным volume с ограничением размера; TLS и
аутентификация завершаются на reverse proxy. Один worker API использует
локальную SQLite spool конкретного задания. Для горизонтального масштаба
задания и временные объекты переносятся в общую очередь/объектное хранилище.

## Защитные пределы

- максимальный размер загрузки настраивается;
- для ZIP-книг ограничиваются распакованный размер и коэффициент сжатия;
- расширение сверяется с сигнатурой;
- листы и колонки выбираются из реально прочитанных метаданных;
- пользовательские имена файлов не используются как системные пути;
- номера в технических сообщениях маскируются;
- CSV-отчеты защищены от formula injection;
- очистка TTL запускается при старте и периодически.
