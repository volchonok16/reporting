# Безопасность и эксплуатация

## Граница доверия

Все загрузки считаются недоверенными. Формат определяется по содержимому и
сверяется с расширением. ZIP-книги проверяются до публикации: ограничены число
элементов, распакованный размер и коэффициент сжатия; запрещены traversal,
символические ссылки и зашифрованные архивы. XLS/XLSB/XLSX не вычисляют
формулы, не запускают макросы и не открывают внешние ссылки.

Номера остаются строковыми идентификаторами. Формулы, дробные, отрицательные и
нечисловые значения отклоняются. Технические отчеты маскируют A/B и экранируют
значения, начинающиеся с `=`, `+`, `-` или `@`.

## Владение и приватность

`X-Session-ID` задает владельца загрузок, заданий и результатов. Запрос из
другой сессии получает `404`, чтобы не раскрывать существование объекта.
Системные пути не возвращаются. Пользовательское имя файла используется
только как безопасное отображаемое имя; хранилище использует случайные имена.

Сессия — не полноценная аутентификация. В production reverse proxy обязан
аутентифицировать пользователя, выпускать непредсказуемый session ID, применять
rate limit и TLS. Не принимайте выбираемый пользователем session ID как
доказательство личности.

## Временное хранение и TTL

Оригинал сохраняется неизменяемой копией. Результат публикуется атомарно после
успешного экспорта. Объекты очищаются при старте и периодически:

- `CAROUSEL_OBJECT_TTL_SECONDS` — срок жизни, по умолчанию 24 часа;
- `CAROUSEL_CLEANUP_INTERVAL_SECONDS` — период очистки, по умолчанию 5 минут.

Compose использует ограниченный `tmpfs` `/data`, поэтому данные исчезают после
удаления контейнера/перезагрузки хоста. Это удобно локально, но не заменяет
production-хранилище. Если результаты должны переживать рестарт, подключите
отдельный зашифрованный volume с квотой и процедурой гарантированного удаления.
Не помещайте чувствительные workspace в логи, backups или image layers.

## Контейнеры

API и web работают под UID/GID `10001`, без Linux capabilities и с
`no-new-privileges`. Compose задает healthchecks, CPU/RAM/PID limits и один API
worker: локальный SQLite spool принадлежит конкретному процессу. Для нескольких
реплик используйте внешнюю очередь заданий и объектное хранилище.

Перед production:

1. Завершите TLS, аутентификацию, лимит тела и rate limiting на reverse proxy.
2. Ограничьте CORS точными production-origin.
3. Закрепите базовые образы по digest и включите сканирование зависимостей.
4. Настройте read-only root filesystem, оставив writable только `/data` и
   минимальные runtime tmpfs, если выбранный frontend runtime это допускает.
5. Отправляйте только агрегированные метрики и маскированные ошибки.
6. Проверьте восстановление после отмены/рестарта и фактическую очистку TTL.

## Остаточные риски

- `X-Session-ID` без внешней аутентификации можно похитить или подобрать при
  слабом генераторе клиента.
- Ограничение tmpfs — общий защитный предел контейнера; параллельные задания
  делят его.
- OLE/XLS не имеет ZIP-ratio защиты, поэтому общий лимит загрузки и ресурсные
  лимиты контейнера остаются обязательными.
- Антивирусное/CDR-сканирование не входит в локальную поставку.
