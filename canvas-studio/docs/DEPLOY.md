# Развёртывание на VPS

Инструкция для того, кто разворачивает (человек или Claude Code в терминале). Сервер — собственный код на Node.js без внешних пакетов. На VPS ставятся только системные вещи: Node.js 22 с nodejs.org (контрольная сумма проверяется), nginx, certbot (если есть домен) и ufw.

## Пошагово, если вы не разработчик

Ниже — всё по шагам. Команды копируйте целиком, весь серый блок: выделить мышью → скопировать → вставить в окно терминала → Enter. Строки, которые начинаются с `#`, — пояснения, их можно копировать вместе с командой: терминал их пропускает.

Скрипты выкладки написаны для **bash** и работают на **macOS** и **Linux**. На **Windows** — через WSL (встроенный в Windows Linux, ставится одной командой, см. шаг 1). Где команды для систем различаются, ниже даны **отдельные варианты: macOS / Windows (WSL) / Linux** — берите свой. Где вариант один, он одинаков для всех.

> Проверено на macOS (zsh и bash). На Windows (WSL) и Linux эти шаги по системе не прогонялись — команды стандартные для Ubuntu, но если где-то ответ отличается от описанного, сообщите.

### 0. Что подготовить

1. **Сервер (VPS).** Купить у хостинга (Beget, Timeweb, Selectel…) VPS с системой **Ubuntu 24.04** (или 22.04, или Debian 12). Хватит самого маленького: 1–2 ядра, 2 ГБ памяти. Хостинг пришлёт (в письме или в панели) **IP-адрес** (вида `159.194.250.13`) и **пароль пользователя root**.
2. **Домен** (если сайт будет по адресу, а не по IP). В панели, где куплен домен (для simmetrika.online — Beget → DNS), поставить **A-запись** `@` → IP сервера и **A-запись** `www` → тот же IP. Записи расходятся по интернету от нескольких минут до пары часов — пока не разошлись, сертификат HTTPS не выпустится (скрипт об этом напишет; тогда просто запустить его ещё раз позже).
3. **Секреты под рукой:** адрес ящика для писем и пароль от него (сейчас — no-reply@simmetrika.online на Beget) и ключ нейросети (нейрошлюз Beget). Если чего-то нет — не страшно: сайт заработает, только без писем или без нейросети; добавить можно потом (шаг 6).

### 1. Открыть терминал

**macOS.** Нажать **⌘ Пробел** (поиск Spotlight), набрать **Терминал** (или Terminal), Enter. Откроется окно с мигающим курсором — сюда вставляются команды (вставка — ⌘V).

**Windows (WSL).** Один раз установить WSL: меню «Пуск» → набрать **PowerShell** → правой кнопкой → **«Запуск от имени администратора»** → выполнить

```powershell
wsl --install -d Ubuntu
```

перезагрузить компьютер; после перезагрузки откроется окно Ubuntu и попросит придумать имя пользователя и пароль (это пароль только для этого Linux внутри Windows — запомните его, он понадобится для `sudo`). Дальше каждый раз: «Пуск» → **Ubuntu**. Вставка в окно — правой кнопкой мыши или Ctrl+Shift+V.

**Linux.** Открыть программу **Терминал** (обычно Ctrl+Alt+T). Вставка — Ctrl+Shift+V.

### 2. Перейти в папку проекта

**macOS:**

```bash
cd ~/Desktop/canvas-studio
```

`~` — ваша домашняя папка, `~/Desktop/canvas-studio` — папка проекта на рабочем столе.

**Windows (WSL)** — папка лежит на диске Windows, из Ubuntu он виден как `/mnt/c`. Вместо `ИМЯ` — имя вашей папки пользователя Windows (как в `C:\Users\ИМЯ`):

```bash
cd /mnt/c/Users/ИМЯ/Desktop/canvas-studio
```

Если рабочий стол в OneDrive, путь бывает `/mnt/c/Users/ИМЯ/OneDrive/Desktop/canvas-studio`.

**Linux:**

```bash
cd ~/Desktop/canvas-studio
```

(или `cd ~/Рабочий\ стол/canvas-studio` — где лежит папка).

Если терминал ответил `no such file or directory` — папки по этому пути нет. На macOS и Linux можно напечатать `cd ` (с пробелом), перетащить папку проекта мышью в окно терминала и нажать Enter — путь подставится сам.

Проверка, что вы на месте:

```bash
ls tools/deploy
```

Должно показать `deploy.sh  harden-ssh.sh  remote-setup.sh  switch-domain.sh`.

### 3. Проверить Node.js и поставить TypeScript

```bash
node -v
```

Должно напечатать версию `v22.13.0` или больше (`v24.16.0` — тоже хорошо). Если `command not found` или версия меньше 22.13 — установить:

**macOS.** Скачать установщик **LTS** с https://nodejs.org, установить как обычную программу, **закрыть и заново открыть Терминал**, повторить шаги 2–3.

**Windows (WSL) и Linux (Ubuntu/Debian):**

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs
node -v
```

(`sudo` спросит пароль: в WSL — тот, что придумали при установке Ubuntu; в Linux — пароль от компьютера. При вводе он не виден.)

Один раз — TypeScript, для проверки типов перед выкладкой (см. «Проверка перед выкладкой»); на всех системах одинаково, `sudo` спросит пароль от компьютера (на Windows — от Ubuntu):

```bash
sudo npm i -g typescript
tsc -v
```

`tsc -v` должно напечатать `Version 5.8…` или больше.

### 4. Ввести пароль root (он не будет виден)

**macOS** (Терминал macOS по умолчанию — zsh):

```bash
read -rs "CS_SSH_PASSWORD?Пароль root: "; export CS_SSH_PASSWORD; echo
```

**Windows (WSL) и Linux** (там bash):

```bash
read -rs -p "Пароль root: " CS_SSH_PASSWORD; export CS_SSH_PASSWORD; echo
```

> Если не уверены, какая у вас оболочка: `echo $0` — напечатает `zsh` или `bash` (бывает `-zsh` / `-bash`). Команда для zsh в bash и наоборот не сработает: в bash первая ответит ошибкой, в zsh вторая — «no coprocess».

Терминал напишет `Пароль root:` — вставьте пароль от хостинга и нажмите Enter. **Символы при вводе не показываются — так и должно быть.** Так пароль не попадает в историю команд и годится любой, даже с кавычками и пробелами.

### 5. Запустить развёртывание

С доменом — вместо `<IP>` подставить IP сервера (без угловых скобок), домен — свой:

```bash
tools/deploy/deploy.sh root@<IP> --domain simmetrika.online --www
```

Например: `tools/deploy/deploy.sh root@203.0.113.10 --domain simmetrika.online --www`.

Без домена (сайт по адресу `http://<IP>`, только чтобы проверить): `tools/deploy/deploy.sh root@<IP>`.

Что вы увидите (всё вместе — 3–10 минут):

| Строка | Что происходит |
| --- | --- |
| `==> Проверка и сборка` | тесты и сборка на вашем компьютере, 1–2 минуты |
| `==> Вход на сервер` | вход на сервер; на новом — по паролю, потом «Ключ этого компьютера положен на сервер» |
| `==> Загрузка версии …`, `==> Настройка сервера` | установка всего нужного на сервер, много строк — это нормально |
| `==> Секреты (на сервере их ещё нет)…` | **вопросы** — см. ниже |
| `==> Вход по паролю` → «Вход по паролю отключён…» | сервер закрыт от подбора пароля, дальше вход только с вашего компьютера по ключу |
| `Готово.` | всё |

**Вопросы о секретах** (отвечать и нажимать Enter; пустой Enter — пропустить):

- `Ящик для писем` — например `no-reply@simmetrika.online`;
- `Пароль от ящика` — ввод не виден;
- `SMTP-сервер [smtp.beget.com]` и `Порт [465]` — для Beget просто Enter (в скобках — то, что подставится само);
- `Ключ нейросети` — ввод не виден.

После ответов скрипт напишет, подхватилось ли: `Почта: no-reply@… через smtp.beget.com:465` и `Макеты по описанию: deepseek-v4-flash`. Если вместо этого «Почта не настроена» или «Макеты по описанию выключены» — значит, ответ был пустым; добавить можно в шаге 6.

Когда закончилось — забыть пароль в этом окне терминала (одинаково на всех системах):

```bash
unset CS_SSH_PASSWORD
```

### 6. Проверить сайт

Открыть в браузере `https://ваш-домен` (или `http://<IP>`), зарегистрироваться — **первый зарегистрированный становится владельцем**. Проверить «Забыли пароль?» (должно прийти письмо) и ✦ «Макет по описанию».

Добавить или поменять секреты потом (одинаково на всех системах):

1. Шаги 1–2 — открыть терминал и перейти в папку проекта (свой вариант системы).
2. Создать в папке проекта файл с секретами:

   ```bash
   nano env.txt
   ```

   Откроется простой редактор прямо в терминале. Вставить строки из разделов «Почта» и «Нейросеть» ниже, со своими значениями. Сохранить и выйти: **Ctrl+O**, Enter, **Ctrl+X** (на Mac тоже Ctrl, не ⌘).
3. Отправить на сервер и удалить файл с компьютера (он уже на сервере):

   ```bash
   tools/deploy/deploy.sh root@<IP> --domain simmetrika.online --www --env env.txt
   rm env.txt
   ```

Файл `env.txt` git не сохраняет (он в `.gitignore`), но пароли в нём лежат открыто — не забывайте `rm env.txt`.

### Обновить сайт потом (после правок)

Шаги 1–2 (свой вариант системы), затем одна команда — та же, но **без** шага 4 (пароль больше не нужен):

```bash
tools/deploy/deploy.sh root@<IP> --domain simmetrika.online --www
```

Для нынешнего рабочего сервера — точно эта строка:

```bash
tools/deploy/deploy.sh root@159.194.250.13 --domain simmetrika.online --www --redirect-from canvas.typehero.online
```

### Если что-то пошло не так

- **`Сервер не пускает по ключу этого компьютера…`** — это новый сервер, а пароль не введён: сделать шаг 4 и повторить шаг 5.
- **`Не удалось войти по паролю`** — пароль неверный: проверить в панели хостинга (там обычно можно сбросить пароль root), повторить шаги 4–5.
- **`Сервер не принимает подключения` / `Connection timed out`** — сервер ещё не запущен (подождать пару минут после покупки) или мешает VPN на компьютере: выключить VPN и повторить. Подробнее — раздел «Если выкладка не проходит».
- **`Тесты не прошли — выкладка отменена`** — в коде ошибка, на сервер ничего не ушло, сайт работает как раньше. Подробности: `npm test`.
- **`Permission denied` при запуске `tools/deploy/deploy.sh`** — файл потерял право на запуск (бывает после копирования): `chmod +x tools/deploy/*.sh` и повторить.
- **`bad interpreter` или `$'\r': command not found`** (бывает на Windows, если папку копировали через Windows-программы, которые меняют переводы строк) — в папке проекта: `sed -i 's/\r$//' tools/deploy/*.sh` и повторить.
- **`read: -p: no coprocess`** (zsh) или **`read: … not a valid identifier`** (bash) — команда шага 4 не для вашей оболочки: взять другой вариант шага 4.
- Ошибка про сертификат / certbot — домен ещё не смотрит на сервер (шаг 0.2): подождать и повторить шаг 5 — повторный запуск безопасен, он ничего не ломает.

Любую команду можно спокойно запускать повторно: скрипт каждый раз проверяет, что уже сделано.

## Что нужно

- VPS на Ubuntu 22.04/24.04 или Debian 12, доступ по SSH под root.
- На машине, с которой разворачиваем: `bash`, `ssh`, `tar`, Node.js 22.13+ (для сборки и тестов).
- Для HTTPS — домен, A-запись которого указывает на IP сервера. Без домена сервер работает по HTTP на IP. Этого хватит, чтобы проверить работу, но для настоящей работы HTTPS обязателен: вход по паролю без него небезопасен.

Пароли и ключи в репозиторий не записываются.

## ⚠️ Чего нет в проекте — без этого сайт работает не полностью

Проект (`~/Desktop/canvas-studio`) — это код и автоматическая настройка сервера. Одна команда `deploy.sh` разворачивает рабочее приложение: редактор, регистрацию, файлы, совместную работу. **Но четыре вещи живут только на рабочем сервере**, их нужно перенести или задать руками:

| Что | Где на сервере | Без этого |
| --- | --- | --- |
| Секреты: почта и ключ нейросети | `/etc/canvas-studio/env` (только root) | `remote-setup.sh` создаёт файл **пустым**. Письма с кодом восстановления пароля не уходят, а пишутся в журнал. Не работает всё на нейросети: «Макет по описанию», «Изменить по описанию» (и для слайдов), «Придумать тексты», заметки к слайду, «Переименовать слои» (остаются только правила). Список строк — в разделах «Почта» и «Нейросеть» ниже. |
| Данные: аккаунты, сессии, файлы пользователей | `/var/lib/canvas-studio` | На новом сервере база пустая: ни одного пользователя и файла. |
| DNS домена | панель Beget, A-записи `@` и `www` | Сертификат не выпустится, сайт по домену не откроется. |
| SSH-ключ этого компьютера | `~/.ssh/authorized_keys` на сервере | `deploy.sh` кладёт ключ сам (на новом сервере, с паролем root) и потом выключает вход по паролю. С **другого** компьютера без его ключа на сервер не войти — только через консоль хостинга. |

Резервные копии данных (`/var/backups/canvas-studio`) лежат **на том же сервере**: если сервер пропадёт, пропадут и они. Перед переездом и время от времени забирайте свежую копию к себе (как — в разделе «Переезд на другой сервер»).

## ⚠️ HTTPS обязателен навсегда (HSTS, с 1 ноября 2026)

С доменом (`CS_SECURE=1`) сервер в каждом ответе отдаёт `Strict-Transport-Security: max-age=31536000`: браузер, хоть раз открывший сайт, **год** не пойдёт на него по http. Если сертификат пропадёт или домен переедет без HTTPS, у этих людей сайт **не откроется совсем** (кнопки «всё равно открыть» не будет). Поэтому: сертификат не отключать, при переезде на новый домен сначала выпустить сертификат на нём; старый домен оставить с HTTPS и перенаправлением 301. Поддомены заголовок не затрагивает (`includeSubDomains` нет — на `typehero.online` живёт другой проект).

## ⚠️ Проверка перед выкладкой: тесты — да, типы — только если стоит TypeScript

- `deploy.sh` сам прогоняет тесты и при падении отменяет выкладку.
- **Проверку типов `deploy.sh` не запускает.** А `npm run typecheck` без установленного TypeScript **не проверяет ничего и всё равно завершается успешно** — печатает «tsc не найден: проверка типов пропущена». Код 0 здесь **не значит**, что типы в порядке.
- Поэтому перед каждой выкладкой: `npm run typecheck` и убедиться, что в выводе есть строка **«Проверка типов (Version …)»** без ошибок. Нужен TypeScript **5.8 или новее** (5.6 не знает опции `erasableSyntaxOnly` из `tsconfig.json`): `npm i -g typescript`.

## Первый раз — одна команда

Новый VPS (чистый Ubuntu/Debian, root с паролем от хостинга). Если нужен домен, его A-записи заранее направить на IP сервера.

```bash
CS_SSH_PASSWORD='пароль root' tools/deploy/deploy.sh root@<IP> --domain simmetrika.online --www
```

Без домена — то же без `--domain` и `--www` (сайт по HTTP на IP, только для проверки). Запускать в терминале: скрипт задаёт вопросы.

Что происходит по порядку:

1. Проверяет, что на этом компьютере Node.js 22.13+, прогоняет тесты и собирает приложение. Тесты упали — выкладка отменяется, на сервер ничего не ушло.
2. **Ключ.** Пробует войти по SSH-ключу этого компьютера (нет ключа — создаёт `~/.ssh/id_ed25519`). Сервер не пускает — входит один раз по паролю из `CS_SSH_PASSWORD`, кладёт ключ и дальше работает только по ключу. Не пустил и по паролю — выкладка отменяется.
3. **Установка.** Загружает версию и запускает `remote-setup.sh`: Node.js, nginx, certbot, ufw, служба, HTTPS, брандмауэр, резервные копии (подробно — «Что делает скрипт»).
4. **Секреты.** Если на сервере файла секретов ещё нет (пустой), спрашивает: ящик для писем, пароль от него (ввод не виден), SMTP-сервер (по умолчанию `smtp.beget.com`), порт (по умолчанию 465), ключ нейросети (ввод не виден). Пустой ответ — пропустить: сайт заработает без почты или без нейросети. Записывает в `/etc/canvas-studio/env` (только root; на этом компьютере не сохраняется), перезапускает службу и печатает, подхватились ли почта и нейросеть. Вместо вопросов можно передать готовый файл: `--env путь/к/env` (что в нём — «Почта» и «Нейросеть»).
5. **Вход по паролю.** Новым подключением проверяет, что ключ работает, и только тогда выключает вход по паролю (`harden-ssh.sh`). Оставить пароль — `--keep-password`.

Если запустить не в терминале (вопросы задать некому), шаг 4 пропускается с предупреждением «секретов на сервере нет» — их можно передать потом той же командой с `--env`.

`--closed` закрывает регистрацию: зарегистрироваться сможет только первый пользователь (владелец). Без флага регистрация открыта. `--email` — почта для Let's Encrypt.

**Что проверено (29.10.2026).** Обновление рабочего сервера этой командой (ничего не спросило и не тронуло), остановка с подсказкой, когда сервер не пускает по ключу, остановка при неверном пароле. **Ещё не проверено:** полный путь на чистом VPS (вопросы о секретах, запись `env`, выключение пароля после установки ключа) и чтение systemd пароля с символами `"` и `\` — свободного сервера для пробы не было. При первом настоящем развёртывании проверить по списку в конце «Переезда на другой сервер».

Пароль root передаётся только в переменной окружения этой одной команды (ssh получает его через `SSH_ASKPASS`, в файлы он не пишется). После выкладки вход по паролю выключен, и пароль больше не нужен.

## Обновление

Та же команда, что при первом развёртывании (с теми же `--domain`/`--email`), только без `CS_SSH_PASSWORD`. Ключ уже на месте, секреты заполнены, вход по паролю выключен — поэтому обновление ничего не спрашивает и ничего из этого не трогает:

```bash
tools/deploy/deploy.sh root@<IP> [--domain …]
```

Рабочий сервер (с 13 октября 2026 — https://simmetrika.online; `www` и прежний `canvas.typehero.online` постоянно перенаправляют на него с тем же путём):

```bash
tools/deploy/deploy.sh root@159.194.250.13 --domain simmetrika.online --www --redirect-from canvas.typehero.online
```

Без `--www` и `--redirect-from` эти адреса перестанут перенаправлять. На каждый адрес выпускается свой сертификат.

## Переезд на новый домен

`tools/deploy/switch-domain.sh` переключает сам, как только домен заработал. Он ставится на сервер в `/usr/local/sbin` и запускается cron каждые 5 минут (как именно — в начале скрипта). Пока общедоступные DNS (8.8.8.8 и 1.1.1.1) не указывают домен на сервер, он ничего не делает. Потом:

1. выпускает сертификаты (не вышло — ничего не меняется, старый адрес работает, через 5 минут ещё попытка);
2. берёт настройки почты из `/etc/canvas-studio/env.<имя домена>`, прежние сохраняет в `env.before-<домен>`;
3. запускает `remote-setup.sh` текущей версии с новым доменом, `--www` (если `www` тоже указывает сюда) и перенаправлением со старого адреса;
4. убирает себя из cron.

Что делает скрипт:

1. Прогоняет тесты. Если они упали, выкладка отменяется. Типы **не** проверяет — см. раздел «Проверка перед выкладкой».
2. Собирает веб-приложение (`dist/`).
3. Входит по ключу (на новом сервере — кладёт ключ, войдя по паролю; см. «Первый раз»).
4. Загружает в `/opt/canvas-studio/releases/<дата-время>` только `dist/`, код сервера и `package.json`.
5. Запускает на сервере `tools/deploy/remote-setup.sh`. Скрипт можно запускать сколько угодно раз: каждый шаг сначала проверяет, что уже сделано.
   - ставит Node.js 22, nginx и ufw (и certbot, если указан домен);
   - создаёт системного пользователя `canvas` и каталоги;
   - переключает `/opt/canvas-studio/current` на новую версию и перезапускает службу `canvas-studio`. Хранятся пять последних версий;
   - настраивает nginx (прокси на 127.0.0.1:8080, gzip — CSS, JS, JSON и файлы «в две строки» `application/x-ndjson`, PERF-004; WebSocket, загрузки до 80 МБ), HTTPS с переадресацией с HTTP, брандмауэр (только SSH, 80 и 443) и ежедневную резервную копию данных;
   - в конце проверяет `/api/health` и печатает адрес.
6. Секреты: спрашивает, если их на сервере нет, или берёт из `--env`.
7. Выключает вход по паролю, если он ещё включён и ключ работает (кроме `--keep-password`).

Прежние отдельные шаги остались для особых случаев: `deploy.sh root@<IP> --install-key` — только положить ключ, `harden-ssh.sh root@<IP>` — только выключить пароль.

## Где что лежит на сервере

| Что | Где |
| --- | --- |
| Приложение | `/opt/canvas-studio/current` → `releases/<версия>` |
| Данные (аккаунты, сессии, файлы) | `/var/lib/canvas-studio` (только для пользователя `canvas`) |
| Резервные копии | `/var/backups/canvas-studio/data-ГГГГ-ММ-ДД.tgz`, 14 дней; **только для root** (каталог 700, файлы 600): в них все данные людей. Права ставит `remote-setup.sh` при каждом деплое, в том числе на копии, сделанные раньше (BUG-158). Забирать копию к себе — через `ssh root@…` |
| Служба | `systemctl status canvas-studio`, журнал: `journalctl -u canvas-studio -f` |
| nginx | `/etc/nginx/sites-available/canvas-studio` |
| Настройки почты (секреты) | `/etc/canvas-studio/env` (только root) |
| Нейросеть «Удалить фон» (70 МБ) | `/opt/canvas-studio/heavy` — **вне версий**, см. ниже |

Служба работает в песочнице systemd: пишет только в каталог данных, без root и без доступа к домашним каталогам.

## Тяжёлые файлы: нейросеть «Удалить фон» (с 1 ноября 2026)

Модель IS-Net и движок ONNX Runtime Web (`apps/web/heavy`, ~70 МБ, лицензии — `apps/web/heavy/NOTICE.md`) **не входят в версию** (`dist`): иначе каждая выкладка весила бы на 70 МБ больше. `deploy.sh` перед «Настройкой сервера» сверяет список файлов с `/opt/canvas-studio/heavy` и докачивает **только отсутствующие** (первая выкладка — минута-другая дольше, дальше ничего). Служба читает папку через `CS_HEAVY` и отдаёт `/heavy/…` с кешем на год.

- Имена файлов несут версию или хэш (`ort-1.20.1/`, `isnet-u8-ff42d260.onnx`). **Новую модель или движок кладите под новым именем** и меняйте его в `packages/editor/src/ai-cutout.ts`; файл под старым именем не перезаписывать — браузеры держат его год.
- Откат версии папку не трогает: старые файлы остаются, старая версия их найдёт.
- Политика безопасности страницы разрешает `'wasm-unsafe-eval'` (компиляция WebAssembly, без eval строк) — без неё нейросеть не запустится, и вырезка тихо пойдёт старым способом (GrabCut).
- На новом сервере папка заполняется при первой выкладке сама.

```bash
ssh root@<IP> 'ls -1t /opt/canvas-studio/releases'          # версии, новые сверху
ssh root@<IP> 'ln -sfn /opt/canvas-studio/releases/<версия> /opt/canvas-studio/current && systemctl restart canvas-studio'
```

```bash
ssh root@<IP> 'systemctl stop canvas-studio && rm -rf /var/lib/canvas-studio && tar -xzf /var/backups/canvas-studio/data-<дата>.tgz -C /var/lib && chown -R canvas:canvas /var/lib/canvas-studio && systemctl start canvas-studio'
```

## Настройки сервера

Переменные окружения задаются в unit-файле `/etc/systemd/system/canvas-studio.service`. Его пишет `remote-setup.sh`.

| Переменная | Значение |
| --- | --- |
| `CS_HOST`, `CS_PORT` | где слушает сервер (по умолчанию 127.0.0.1:8080, снаружи — только через nginx) |
| `CS_DATA` | каталог данных |
| `CS_SECURE=1` | cookie только по HTTPS (включается вместе с доменом) |
| `CS_TRUST_PROXY=1` | брать адрес клиента из заголовка nginx (для ограничения попыток входа) |
| `CS_OPEN_REGISTRATION=0` | регистрация только первого пользователя |
| `CS_APP_URL` | адрес приложения для писем (ставит `remote-setup.sh`: `https://<домен>` или `http://<IP>`) |

## Почта

Сервер отправляет письма с кодом для восстановления пароля. SMTP-клиент свой, без пакетов (`packages/server/src/mail.ts`). Настройки почты хранятся в `/etc/canvas-studio/env`. Файл читает только root, а `remote-setup.sh` создаёт его пустым и потом не перезаписывает:

```bash
CS_SMTP_HOST=smtp.beget.com
CS_SMTP_PORT=465
CS_SMTP_SECURE=ssl          # ssl — TLS сразу (465), tls — STARTTLS (587), none — без шифрования
CS_SMTP_USER=no-reply@simmetrika.online
CS_SMTP_PASS=…
CS_MAIL_FROM=no-reply@simmetrika.online
CS_MAIL_FROM_NAME=Симметрика
```

После правки: `systemctl restart canvas-studio`. При запуске служба пишет в журнал, через какой сервер идёт почта. Без `CS_SMTP_HOST` письма не отправляются, а попадают в журнал (удобно при локальной разработке). На 159.194.250.13 используется ящик no-reply@simmetrika.online на Beget (до 13 октября 2026 — typehero@typehero.online): SPF домена разрешает отправку только через Beget, поэтому письма идут через smtp.beget.com, а не с самого VPS.

## Нейросеть

Ключ и адрес шлюза — в том же `/etc/canvas-studio/env`:

```bash
CS_AI_KEY=…                                   # ключ нейрошлюза Beget; без него функции на нейросети выключены
CS_AI_URL=https://api-llm.beget.com/v1/       # необязательно, это значение по умолчанию
CS_AI_MODEL=deepseek-v4-flash                 # необязательно, это значение по умолчанию
```

После правки: `systemctl restart canvas-studio`. При запуске служба пишет в журнал «Макеты по описанию: deepseek-v4-flash» или «Макеты по описанию выключены (CS_AI_KEY)» — так видно, подхватился ли ключ.

## Переезд на другой сервер

Старый сервер — `OLD`, новый — `NEW` (оба `root@<IP>`).

```bash
# 1. Выкладка на новый сервер одной командой (домен пока смотрит на старый — без --domain, по IP).
#    На вопросы о секретах ответить пустым: их переносит шаг 2.
CS_SSH_PASSWORD='пароль root' tools/deploy/deploy.sh NEW

# 2. Секреты: файл env со старого сервера на новый (через этот компьютер, на диск не сохраняется).
ssh OLD 'cat /etc/canvas-studio/env' | ssh NEW 'umask 077 && cat > /etc/canvas-studio/env'

# 3. Данные: остановить старый сервер (чтобы не потерять последние правки), перенести, запустить новый.
ssh OLD 'systemctl stop canvas-studio && tar -czf - -C /var/lib canvas-studio' > data-move.tgz
ssh NEW 'systemctl stop canvas-studio && rm -rf /var/lib/canvas-studio && tar -xzf - -C /var/lib && chown -R canvas:canvas /var/lib/canvas-studio && systemctl start canvas-studio' < data-move.tgz

# 4. DNS: в Beget A-записи @ и www → IP нового сервера. Когда обновятся — выкладка с доменом (выпустит сертификаты):
tools/deploy/deploy.sh NEW --domain simmetrika.online --www --redirect-from canvas.typehero.online
```

Проверить на новом сервере: вход в свой аккаунт и файлы на месте; «Забыли пароль?» присылает письмо; ✦ «Макет по описанию» отвечает; в журнале (`journalctl -u canvas-studio -n 20`) есть строки «Почта: …» и «Макеты по описанию: …». Файл `data-move.tgz` содержит все данные пользователей — после переезда удалить или хранить как резервную копию в надёжном месте. Старый сервер не удалять, пока новый не проработал несколько дней.

## Если выкладка не проходит

- **«Connection timed out during banner exchange» или сайт не открывается только с этого компьютера.** Проверить, не включён ли VPN в режиме TUN (AmneziaVPN, incy): он перехватывает маршрут до сервера. Проверка в обход VPN: `curl --interface en0 --resolve simmetrika.online:443:<IP> https://simmetrika.online/api/health`. Выкладка в обход VPN — через обёртку `ssh`, которая выходит через сетевую карту (`ssh -o BindInterface=en0`), положенную в `PATH` перед системной. Если сайт открывается с телефона — сервер исправен, повторять выкладку вслепую не нужно.
- **Сбой посреди выкладки.** Сначала проверить, не выложилась ли новая версия (сайт отдаёт новое), и только потом повторять. Откат — в разделе «Откат».

## Нагрузочный тест

Перед изменениями сервера и чтобы понять запас:

```bash
node --disable-warning=ExperimentalWarning tools/loadtest/loadtest.ts --files 10 --per 5 --seconds 20 [--image-mb 10] [--pages 3]
```

Сервер запускается отдельным процессом на временной папке. Тест печатает его память и процессор, сообщения в секунду и задержки курсора и правки. На рабочем сервере не запускать.
